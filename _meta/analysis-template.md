# 分析标题

> 当前判断：用一句话说明核心主张、适用范围和当前证据强度。

使用本模板前，先确认问题讨论 Agent 本身的稳定机制。一次对话、单个工具观察或资料汇总不足以单独成为新分析；它们应先作为既有分析的证据指针，除非已经形成可独立审查的问题。

修订既有文章时，先复核它是否仍拥有独立问题、当前判断是否仍有证据、去掉实现名称后机制是否成立，以及它是否仍会改变实际决定。若不再成立，不要机械填充模板；按写作规范提出精确的合并与退出清单，并在获得所需的结构确认后执行。

## 1. 问题是什么

分开描述可观察现象、用户或 Agent 的初始解释，以及真正需要回答的问题。

## 2. 为什么这是 Agent 的基础问题

说明该问题为什么跨模型、工具或任务环境仍然成立。若只能由某一实现解释，应留在其领域仓库。

## 3. 相关概念及边界

用功能和责任定义关键术语，不用当前产品名称代替概念。区分稳定对象、当前活动和实现例子。

## 4. 已有证据

区分直接证据、结构类比和工程推断。证据较多时可使用：

| 证据与来源 | 认识论角色 | 能支持的判断 | 不能推出的结论 | 版本、时间与适用环境 |
|---|---|---|---|---|
|  |  |  |  |  |

具体工具、框架、模型和 API 只作为实现证据；优先使用论文、版本化官方文档、源码 commit 或可复现实验。若引用未版本化实现文档，记录核查日期、受影响的具体主张，以及接口变化后需要重新确认什么。

多条来源支持同一判断时，说明它们是否共享模型、数据、基准、环境、评价器、上游来源或组织激励。并列实现、同源案例和使用相同材料的多个 Agent 不自动构成独立复现。

## 5. 竞争性解释

至少保留一个机制不同、仍然合理的解释，并说明什么新证据能区分它与当前判断。不要把缺少反例写成支持证据。

## 6. 当前判断

明确哪些是已核查事实、结构类比、推断、假设和结论。说明证据强度，不把暂定解释写成定论。

执行工具名删除测试：去掉所有产品、模型和框架名称后，核心问题、因果关系和适用边界是否仍然成立？若不能，解释为什么该实现仍属于 Agent 基础问题，否则继续抽象或退出主线。

## 7. 适用边界与反例

记录适用条件、已知反例、主要未知量，以及什么证据会限制、降低可信度或推翻当前判断。

## 8. 对日常 Agent 使用的意义

只写会改变判断、行动、授权或验收的含义，不扩展成工具清单、配置教程或通用流程。

## 9. 待区分的问题

只保留答案会改变判断、行动、授权、验收或保留决定的问题。为每个问题说明竞争解释和能够区分它们的证据；不要把产品演进预测或方案愿望清单当作研究议程。

## 10. 修订记录

- YYYY-MM-DD：由何种证据或反例触发；原判断怎样改变，证据强度或适用边界怎样调整。

只记录认识和权威边界变化；章节移动、链接整理、格式与措辞变化留给 Git 历史。
