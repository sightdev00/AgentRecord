# 写作与证据规范

这份规范只控制分析质量，不建立额外的知识资产工作流。

## 基本要求

- 把可核查事实、结构类比、推断、假设和当前结论分开；
- 优先引用原始论文、官方文档、源代码、原始数据和可复现实验；
- 二手总结和模型输出可以提供线索，不能独立支撑关键结论；
- 主动寻找反证、竞争解释和失败边界；
- 不把用户观点、历史记忆、流行程度或 Agent 自评当成事实；
- 不为追求完整感补齐未知细节；
- 结论必须说明适用范围及证据强度。

## 外部案例

领域案例只作为证据指针，写清：

- 来源仓库、稳定 URL 或 commit；
- 它支持或反对哪一条判断；
- 从案例到 Agent 机制的映射是直接证据、结构类比还是工程推断。

不要复制案例背景、排查命令、原始结果和解决方案。

### 外部 Agent 工作流与 Skill 仓库

外部 Skill、Prompt 和 Agent 工作流仓库首先是实现证据，不因流程完整、使用频繁或作者经验丰富而成为效果证据。准备把其中内容接入分析时，临时回答：

1. 它针对什么可观察失效，而不是宣称解决什么宽泛问题；
2. 它在哪个责任边界施加控制，由谁触发、执行和判断完成；
3. 什么可检查条件允许当前步骤或判断升级为下一项承诺；
4. 完成信号是否直接对应用户目标，还是只证明流程运行、文件生成或工具调用成功；
5. 它依赖哪些模型、Prompt、Context、工具、运行时、评价器和组织条件；
6. 删除产品名、Skill 名和步骤包装后，哪些失效机制、责任和验收关系仍然成立；
7. 它改变了现有哪项判断、证据强度、适用边界或日常行动。

同一仓库中的多个 Skill、角色或并行 Agent 通常共享作者、模型谱系、材料和成功定义，不能按文件或执行者数量累计为独立证据。若分析只能确认一种机制存在可执行实现，但不能确认其净效果，应明确限定为实现可行性或结构例证。

上述拆解不建立 Skill 索引、案例卡、流程目录或固定状态文件。若外部仓库只增加实现例子，没有改变现有判断、边界或行动，则停止写入；需要复用的实际 Skill、配置和脚本留在其工程仓库或独立项目中。

## 经验怎样进入仓库

用户案例描述、一次对话、任务成功或失败只触发经验筛选，不自动生成新资产。先把描述拆成可观察事件、用户或 Agent 的初始解释、改变判断的纠正或结果，以及能够定位这些内容的制品；不要把叙述、解释和证据合并成一个事实。

1. 没有稳定来源、原始制品或可定位记录时，案例描述只用于定位待核问题，不作为仓库证据；
2. 有领域仓库、稳定 URL、任务记录或 commit 时，把它作为相关分析中的证据指针，并标明哪些内容是直接观察、当事人报告或工程推断；
3. 新证据改变同一问题的判断、边界、反例或不确定性时，修订现有分析；
4. 只有形成独立核心问题，并能单独处理证据、竞争解释和适用边界时，才新增分析；
5. 再次支持已有判断时，补充证据及其独立性和局限，不创建同义原则或平行文章。

完成证据准入后，不直接把案例中的解决方案改写成通用经验。对准备进入分析的判断再做两项检查：

- **行动差异检查**：写清案例前采用了什么判断或行动，哪项可定位证据改变了它，改变后采取什么不同动作，以及结果怎样验收。若案例没有改变判断、边界或行动，只把它视为支持性例子，不新增经验主张；
- **实现替换检查**：先删除案例中的模型、工具、框架、API 和角色名称，把相关能力与约束改写成功能描述，再设想能力等价的其他实现。若问题、责任、失效机制、触发条件和验收仍成立，它可以成为带适用条件的跨工具机制；若判断只能依赖某个实现偶然的接口形状，就只作为带时态和版本边界的实现证据。

两项检查的结果不另建案例卡、原则卡或状态文件。它们分别进入所属分析的证据角色、适用边界和修订理由；领域实现细节仍留在原仓库或原始任务记录中。

一个可定位案例若直接反驳无边界主张，可以促使删除主张或收窄边界；单个案例不能仅凭代表性想象建立通用机制。案例数量也不能单独决定判断强度。还应检查来源独立性、观察方法、适用环境、竞争解释，以及案例到 Agent 机制的映射是否成立。

## 证据独立性

证据是否独立必须相对于当前担心的失效机制判断，不由作者、文件或 Agent 数量决定。提高判断强度前，检查多条证据是否共同依赖：

- 相同模型、训练谱系、Prompt、Context 或工具接口；
- 相同数据、基准、任务分布、环境或组织；
- 相同评价器、Oracle、人工审查者或成功定义；
- 上游共同来源、相互引用的实验结果或同一工程观察；
- 相同商业激励、发布选择和未公开的失败样本。

两个实现文档可以证明一种边界不止一种实现方式，却不能证明该边界提高任务质量；多个 Agent 使用相同材料和评判标准，也不能算独立验收。只有新证据能够沿不同失败路径否定当前判断时，才提高独立支持强度。无法确认独立性时，记录共同依赖或把来源限定为并列例子，不按数量累积可信度。

## 稳定对象优先

文件和目录优先表达跨工具仍然成立的问题、机制与关系。工具、框架、模型和工作流可以作为证据对象或实现例子，不能仅因流行、能力丰富或当前正在使用就成为长期分类轴。

拆分文章的理由应是出现了可以独立审查和引用的问题，不是文件变长。拆出的文章至少应有自己的核心主张、证据、竞争解释、适用边界和未解决问题；否则保留在原分析中，以免制造重复权威来源和同步负担。

## 易变实现证据

引用具体工具、框架、模型或 API 时：

- 优先链接版本化官方文档、论文、源码 commit 或可复现实验；
- 分开记录“该实现当时具有什么结构”和“该结构支持什么一般判断”；
- “当前”“主流”“最佳”“领先”等时效性表述只有在日期和比较范围会改变判断时才保留；
- 工具退场、改名或接口变化时，不为保存历史而扩写产品背景；应检查一般判断是否仍有独立证据，并替换指针、降低证据强度或修订结论；
- 若删除所有产品名后文章的核心问题、因果关系和适用边界无法成立，说明文章仍然依赖实现，应继续抽象或退出主线。

## 证据失效怎样处理

维护由会改变判断的事件触发，不建立定期追新、来源状态表或产品寿命档案。出现以下情况时，重新审查相关主张：

- 原链接失效、文档改版、接口语义变化或论文出现新版本；
- 原文使用“当前”“默认”“支持”等实现事实，而该事实影响结论；
- 某个产品或单篇论文成为一般判断的唯一证据；
- 出现独立复现、反证、撤稿、重大限制或更强的一手来源；
- 新工程观察与既有判断冲突，且差异不能由环境边界解释。

处理顺序是：先重新读取原始来源并确认变化是否实质影响主张；再优先替换为版本化一手来源或稳定 commit；仍无独立支持时，降低证据强度、收窄边界或删除结论；最后在原文章修订记录中说明哪项证据改变了哪项判断。链接仍可访问不等于证据仍有效，产品退场也不自动推翻由其他证据支持的机制。

## 分析怎样退出主线

不建立定期盘点、成熟度标签或 Deprecated 目录。以下事件发生时，随当前任务复核文章是否还应作为独立权威存在：

- 文章被新证据直接修改；
- README 的问题所有权或分析接口发生变化；
- 新分析准备处理相邻问题；
- 核心来源失效，或工具名删除测试不再通过；
- 两篇文章开始重复维护同一主张、证据图或日常含义。

复核只回答四个问题：核心问题是否仍然独立；当前判断是否仍有可定位证据；删除易变实现名称后机制是否仍成立；文章是否仍会改变判断、行动、授权、验收或保留决定。

若答案是否定的，先列出精确的内容合并、链接修正、索引修改和文件删除清单；文件删除或目录变化仍须遵守仓库的结构确认规则。确认后，把仍有效的主张、反例和证据指针合并到真正的问题所有者，修正所有入站链接和 README 索引，再删除失去权威职责的文章。Git 历史保存被取代的文字；不要为历史可见性保留空壳、平行旧版或复杂状态页。若文章得到的是“当前证据不足”或否定结果，但问题仍独立且不确定性会改变行动，则应保留并收窄判断，而不是因为结论不积极就删除。

## 研究优先级与停止条件

主动研究只服务于当前判断，不以新工具、新论文或热门话题本身作为选题理由。开始前先写清：

1. 当前哪项判断或未解决问题会受到影响；
2. 至少两个机制不同的解释或方案；
3. 什么观察能够区分它们；
4. 不同结果会改变哪项行动、授权、验收或保留决定。

优先处理与真实失败冲突的观察、高影响决定中的关键证据缺口、独立反证或复现，以及会使现有证据失效的变化。若新增材料只能增加例子数量，不能改变判断、边界或行动，就停止扩展并保留当前不确定性，等待新的触发事件。

具体实现的新版本只有在改变责任边界、失效模式、证据有效性或当前选择时才值得复核。不要建立定期趋势扫描、产品观察名单或“未来方向”收藏。

## 修订

新证据改变同一个问题时：

1. 直接修订原分析；
2. 修订记录只说明哪项证据或反例改变了哪个判断、证据强度、适用边界或文章权威关系；
3. 不记录章节移动、链接集中、格式调整、措辞润色或被放弃的中间结构；这些过程由 Git 历史保存；
4. 不使用复杂 YAML、成熟度等级或跨目录状态关系。

修订记录是认识变化记录，不是文件 changelog。若无法说清“原判断怎样改变以及为什么”，通常不应新增条目。
