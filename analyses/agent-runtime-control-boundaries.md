# Agent 运行控制的责任边界：从单次采样到持续执行

> 当前判断：本文先按系统必须回答的控制问题划定责任，再用指令内容、本轮决策视图、模型外运行责任和跨轮推进四种关系定位 Prompt、Context、Harness 与 Loop 等当前常用术语。它们不是四个同层组件：指令内容属于本轮决策视图，跨轮推进通常由模型外运行层驱动，显式图只是约束部分状态转移的可选拓扑。长期有效的是控制问题、责任及其失效边界，而不是这些名称、四分法或某种固定组合。

## 1. 问题是什么

仅依赖单次模型调用时，系统行为可能主要受 Prompt 影响。任务涉及检索、工具调用、持续执行或跨会话协作时，Prompt 仍然重要，但已经无法单独解释谁选择材料、谁允许动作、谁保存状态以及谁判断完成。

问题表征、信念与证据、行动承诺、验证与验收的语义由[问题求解控制总论](./agent-problem-solving-control.md)维护；本文只讨论这些区分在系统中的落点与运行关系，不判断具体内容是否正确。

一次 Agent 决策可以近似写成：

\[
C_t=\operatorname{Assemble}(P,U_t,R_t,M_t,T_t,B_t)
\]

\[
Y_t=\operatorname{Model}(C_t)
\]

\[
(S_{t+1},O_t)=\operatorname{Runtime}(S_t,Y_t,\Pi,A,E)
\]

- \(P\)：系统指令、任务要求和输出契约；
- \(U_t\)：当前用户输入；
- \(R_t\)：本轮检索到的外部材料；
- \(M_t\)：会话、长期记忆和结构化工作状态；
- \(T_t\)：可见工具及其描述；
- \(B_t\)：Token、时间、费用和风险预算；
- \(C_t\)：模型在第 \(t\) 轮真正看到的 Context；
- \(Y_t\)：模型产生的文本、结构化输出或候选动作；
- \(S_t\)：模型外部的持久状态；
- \(\Pi\)：权限、门控、重试、停止和恢复策略；
- \(A\)：可执行能力；
- \(E\)：外部环境；
- \(O_t\)：执行结果、错误、测试和人工反馈。

这组符号只示意输入、模型、外部状态和反馈之间的责任关系，不是完备字段集、持久状态 Schema 或实现要求。

当 \(O_t\) 被整理进下一轮输入并再次调用模型时，模型外运行层的调度与策略推动系统形成跨轮重复关系，本文暂借用 Loop 作为这类关系的标签。控制图可以进一步限制 \(\Pi\) 中的允许路径，但图本身既不产生正确 Context，也不保证节点语义正确。

本文要解决三个问题：

1. 输入组织、本轮决策视图、模型外运行责任、跨轮推进和显式控制拓扑怎样嵌套和协作，当前常用术语怎样映射到这些责任；
2. 这些边界由哪些研究和工程证据支持，哪些结论不依赖具体工具名称；
3. 面向具体任务时，怎样选择最小充分结构，并只在证据确认控制缺口时增加结构。

## 2. 功能地图：控制关注点与责任边界

先按系统需要回答的问题划分控制关注点。具体论文、协议和实现文档的证据角色集中在第 5 节维护，避免产品事实散落在多个功能定义中。

本文只把 Prompt、Context、Harness 和 Loop 用作当前术语映射，不让它们承担永久分类。术语消失时，仍按“谁组织本轮输入、谁强制模型外约束、谁保存状态、谁决定继续”定位责任；只要这些问题仍存在，文章的核心判断就不依赖原名称。

| 控制关注点 | 需要回答的问题 | 最小机制 | 主要失效边界 |
|---|---|---|---|
| 指令、示例与输出契约 | 本轮希望模型怎样生成候选 | 指令内容与机械输出检查 | 文本规则不能强制模型外权限或保存真实状态 |
| 外部材料与当前状态视图 | 哪些材料进入这次决策，来源和时态是什么 | 材料选择、标注、排序与刷新 | 检索不等于事实写入，增加材料不保证模型会正确使用 |
| 动作与环境反馈 | 候选怎样影响环境，新观察怎样返回 | 明确动作接口、隔离运行时与结构化反馈 | 动作成功不等于目标完成，反馈也可能错误或不完整 |
| 能力与授权 | 什么可以被发现、提出和实际执行 | 能力注册或协议，以及独立授权策略 | 连接与传输机制不负责业务授权、信任或验收 |
| 状态、事件与恢复 | 什么跨轮保留，失败后从哪里恢复 | typed state、追加事件、制品和检查点 | 持久化也会保存过期假设、压缩错误和污染状态 |
| 继续、停止与依赖关系 | 谁选择下一步，何时停止，失败去哪里 | 有界跨轮推进；必要时使用显式控制图 | 允许路径正确不保证节点内容、问题表征或 Oracle 正确 |
| 人类责任 | 谁理解并决定高影响承诺和最终产物 | 可查看证据、可修改或拒绝的审查边界 | 流程中出现过一个人不等于形成有效监督 |

这些关注点可以组合，但没有固定的加入顺序。选择依据是当前任务暴露了什么控制缺口，以及新增机制是否比现有替代方案更低成本、更可验证。

## 3. 稳定责任与当前常用术语的映射

### 3.1 指令内容：单次采样的局部策略（常称 Prompt）

Prompt 可以包含角色、目标、约束、示例、工具说明、输出 Schema 和评价标准。第 5 节收录的特定模型与基准实验显示，任务描述、示例和中间步骤示例都可能改变被测任务表现。该结果只说明输入组织是性能变量，不说明同一写法能跨模型稳定复现，也不证明生成的中间文本忠实反映内部推理。

适合放进 Prompt 的内容：

- 本次任务目标和受众；
- 必须遵守的语义约束；
- 输出结构与少量高质量示例；
- 当前步骤的评价标准；
- 模型需要知道、但无须由运行时强制的工作方式。

仅写在 Prompt 中的规则属于软约束。权限、费用上限、禁止写入范围、发布门和不可逆动作审批若必须在模型忘记或误解时继续成立，就应由模型外运行层执行。

Prompt 的使用方法可压缩为四步：先写成功条件，再写输入边界；只给能够改变决策的示例；把可机械检查的要求转换成 Schema 或测试；通过任务集评估。单个漂亮输出不足以支持调词结论。

### 3.2 本轮决策视图：可见状态（常称 Context）

Context 是一次推理时送入模型的全部 Token，范围大于用户看到的 Prompt。它可能包含：

```text
系统指令
+ 用户输入
+ 工具定义
+ 检索材料
+ 会话历史
+ 计划与进度
+ 工具结果和错误
+ 记忆摘要
+ 当前环境元数据
```

第 5 节收录的检索增强与长 Context 实验表明，外部材料可以为知识更新和来源追踪提供路径，但相关信息的位置变化也会显著影响表现。增加材料可能提高召回，也会增加模型实际利用信息的难度。

本轮决策视图的组织因而是一项持续选择工作：

1. **选择**：只引入能改变当前决策的材料；
2. **标注**：保留来源、时间、作用域、可信度和版本；
3. **排序**：让目标、当前状态和关键证据处在稳定、易定位的位置；
4. **压缩**：把旧轨迹转成结构化事实、未决问题和制品指针；
5. **隔离**：区分执行 Context、诊断 Context、敏感数据和对外输出；
6. **刷新**：对可能变化的事实重新获取，不让摘要冒充当前状态。

本轮决策视图不是长期记忆本身。数据库、文件、事件日志和知识库保存在模型外；当前常说的 Context 只是模型外运行层在某一轮为某一决策生成的视图。

### 3.3 模型外运行责任（本文暂称 Harness）

Harness 没有唯一行业定义。本文将其定义为：围绕模型调用，负责准备输入、解释输出、连接能力、执行策略、持久化事实并提供反馈的系统层。

本文保留 Harness 作为工作术语，而非押注某个产品类别。只要“模型外部负责输入组装、能力执行、策略强制、状态保存和反馈”的责任仍然存在，行业名称变化不改变这条边界；若这些责任被模型或其他系统吸收，则应重新划界。

按本文的功能定义，Harness 可以包含：

| 组件 | 职责 | 关键设计问题 |
|---|---|---|
| Context assembler | 从指令、检索、记忆、历史和工具中构造 \(C_t\) | 哪些内容进入本轮，为什么，何时失效 |
| Model adapter | 调用模型并约束结构化输出 | 超时、重试、模型切换和解析失败如何处理 |
| Tool / ACI registry | 向模型暴露可理解的动作 | 工具粒度、名称、Schema、返回内容和副作用 |
| Runtime / sandbox | 在文件、终端、浏览器或 API 环境中执行动作 | 权限、隔离、网络、密钥和资源上限 |
| State / artifact store | 保存计划、事件、制品、检查点和决策 | 哪些是事实，哪些可更新，哪些必须追加保存 |
| Policy / guardrail | 检查授权、风险、预算与输入输出 | 哪些规则必须独立于模型执行 |
| Scheduler | 决定 ready set、并发、handoff 和停止 | 谁拥有下一步选择权，怎样避免无限循环 |
| Trace / evaluator | 记录轨迹并用测试、评分器或人工检查 | 证据是否新鲜，验收是否与执行相关失败 |
| Recovery / human control | 暂停、批准、拒绝、回滚、重规划和接管 | 人能否理解当前状态并作出有效决定 |

第 5 节收录的软件工程 Agent 研究分别说明，动作语言、反馈格式、事件记录和执行环境都可能成为性能变量。它们同属代码任务与平台研究谱系，可能共享模型、基准和评价方法，不能按论文数量视为独立复现。工具设计也会改变本轮决策视图：模糊、重叠的动作会消耗选择能力，一次返回过多数据会污染后续推理。相关厂商工程记录提供了设计线索，但需要在具体模型与任务集上重新评估，不能当成恒定规律。

### 3.4 跨轮推进关系（本文暂称 Loop）

跨轮运行需要完成一组有边界的状态转移，本文用 Loop 指这组由运行时驱动的重复关系。一个可控循环至少包含：

```text
Observe
→ Assemble Context
→ Propose
→ Authorize
→ Execute
→ Verify
→ Commit State
→ Continue / Replan / Stop / Escalate
```

第 5 节收录的行动—观察实验显示，外部动作和新观察可以改善部分交互任务，也会产生误读观察、重复动作等轨迹级失败；相关概念框架则说明，每轮可以读取记忆、进行内部推理、选择外部动作并接收新观察。这些材料支持把跨轮状态转移作为独立控制问题，不证明某一种循环模板普遍适用。

运行时推进这组跨轮关系时需要显式设置：

- 最大轮数、费用、时间和副作用预算；
- 每种错误可原样重试几次，何时必须换策略；
- 哪些观察可以更新事实，哪些只能进入候选证据；
- 完成条件由谁判断，需要什么新鲜证据；
- 何时暂停给人审查，怎样序列化并恢复；
- 轨迹怎样压缩，同时保留原始事件和制品。

一种常见循环运行方式是：模型返回最终候选时停止，返回交接时切换执行者，返回动作请求时执行并把结果送入下一轮，同时用最大轮数限制循环；状态、策略门和轨迹记录由模型外组件处理。第 5 节的实现快照证明这种边界可以落地，不代表任何默认终态足以证明用户目标已经完成。

### 3.5 显式控制拓扑（常以图表达）

控制图描述允许或计划中的执行关系。节点可以是动作、检查点、人工审查或子流程；边可以表达依赖、条件、数据传递、失败转移和授权门。

以下关系容易被混淆：

- **控制图**：规定哪些状态与转移被允许；
- **执行轨迹**：记录一次运行实际发生的事件；
- **思维图**：表达推理单元之间的依赖或组合；
- **知识图**：表达实体与语义关系；
- **Loop**：驱动运行时不断推进的循环机制。

图执行器通常仍由事件循环驱动，因此图与 Loop 可以同时存在。代表性实现使用 typed state、节点、边、检查点和中断：图定义控制结构，持久化支持恢复，中断把状态交给人检查和修改；相应实现快照集中在第 5 节。

一张图只有在边和节点具有可执行语义时才算显式。每个节点至少应说明输入、输出契约、权限、预算、终态、验收和失败去向。计划需要改变时，应创建新版本并保留旧版本的停止位置与修订原因。

### 3.6 稳定责任、工作术语与拓扑之间的关系

这些操作视角与可选拓扑可以压缩成以下关系：

```text
Instruction content ⊂ Decision view_t

Model-external runtime --构造--> Decision view_t
Model-external runtime --解释与执行--> Model output
Model-external runtime --保存--> State / Events / Artifacts

Runtime scheduler --推进--> Model + Environment
Cross-turn progression := Runtime + Model + Environment 的重复交互

Control topology --约束--> 跨轮推进中允许的状态与转移
Human review --决定--> 关键承诺、发布与接管
```

模型负责生成候选；模型外运行层决定候选怎样接触真实环境，并依据调度与策略推进、暂停或停止；跨轮推进描述这组交互的重复关系；图把部分调度策略固定成可检查结构；人对高影响承诺和最终产物承担决定责任。Prompt、Context、Harness 和 Loop 分别可映射到指令内容、本轮决策视图、模型外运行责任和跨轮推进，但不定义这些责任。

## 4. 可替换的实现模式

下表按控制机制而不是产品分类。同一工具可能组合多种模式，同一模式也可以由不同框架或自建代码实现。

| 实现模式 | 最小结构 | 适用条件 | 主要边界 |
|---|---|---|---|
| 指令与示例驱动的单次调用 | `instruction + examples + input → output` | 目标固定、无副作用、结果易检查 | 不持久化真实状态，文本规则不能强制权限 |
| 检索增强的输入组装 | `query → retrieve → select → context → output` | 需要外部、可更新且可追溯的材料 | 检索、选择、冲突处理和 Context 利用都可能失败 |
| 行动—观察循环 | `propose → act → observe → update` | 路径不能预先确定，需要环境反馈 | 历史膨胀、重复动作、错误状态提交和虚假完成 |
| 受约束的动作接口与隔离运行时 | 小型动作语言 + 明确反馈 + 权限/沙箱 | 模型需要接触文件、终端、浏览器或 API | 接口对模型和任务敏感，隔离不证明动作正确 |
| 能力协议 | 能力发现 + 输入输出契约 + 宿主—客户端责任边界 | 多来源能力需要互通和替换 | 协议不负责业务授权、调度与验收 |
| 持久状态与检查点 | typed state + event/artifact store + resume | 跨轮或跨会话任务需要恢复与追溯 | 过期状态、压缩错误和恢复语义仍需治理 |
| 显式工作流或控制图 | nodes + transitions + gates + failure paths | 分支、并发、审计或恢复关系值得固定 | 图正确不等于节点内容正确，静态结构会固化假设 |
| 长时任务交接 | initializer/planner + incremental worker + evaluator + artifacts | 工作跨越多个 Context window 或执行者 | 评价器漂移、交接损失和脚手架过时 |

选择顺序应是“需要控制什么 → 最小机制是什么 → 哪种实现满足条件”。产品比较只能发生在最后一步，并应在模型、任务或接口变化后重新评测。

## 5. 证据映射与当前强度

这些材料分别回答“某机制在特定实验中是否有效”“某控制边界是否可实现”和“某结构能否被形式化”。它们不能合并成一条从 Prompt 必然演进到图执行的历史规律。

| 来源 | 证据角色 | 能支持什么 | 不能推出什么 | 时态与有效边界 |
|---|---|---|---|---|
| [GPT-3 v4](https://arxiv.org/abs/2005.14165v4)、[Chain-of-Thought v6](https://arxiv.org/abs/2201.11903v6) | 特定模型与基准上的直接实验 | 指令、示例和中间步骤示例会改变被测任务表现 | Prompt 能强制模型外权限、保证推理忠实或跨模型稳定复现 | 两项研究处理不同输入干预与任务，不是同一效应的独立复现；模型、规模和任务改变后需重测 |
| [RAG v4](https://arxiv.org/abs/2005.11401v4)、[Lost in the Middle](https://arxiv.org/abs/2307.03172v3) | 检索实验与长 Context 行为实验 | 外部材料的检索、选择和位置会影响输出 | 任意现代检索系统都更可靠；增加 Context 总会提高质量 | 两项研究分别处理检索增强和位置效应，不构成同一主张的复现；结论受模型、检索器、材料分布和任务影响 |
| [ReAct](https://arxiv.org/abs/2210.03629v3) | 行动—观察交错的基准实验与轨迹分析 | 外部行动和新观察可以改善部分交互任务，也会产生轨迹级失败 | 该循环具有充分停止规则；同一生成器的自评可独立验收 | 论文中的任务与工具环境，不是任意生产 Loop |
| [SWE-agent](https://arxiv.org/abs/2405.15793v3)、[OpenHands](https://arxiv.org/abs/2407.16741v3) | 软件工程 Agent 的接口、平台与基准研究 | 动作接口、反馈格式、事件流和运行环境是性能变量 | 论文平台结构可直接迁移；平台贡献与具体 Agent 策略完全可分 | 同属代码任务与平台研究，可能共享模型、基准和评价方法；不是接口因果效应的独立复现 |

## 6. 当前判断：只为已证实的控制缺口增加结构

下面不是成熟度等级。复杂结构不天然优于简单结构；增加组件、循环或图之前，应先证明当前结构存在无法以更小代价处理的控制缺口。

| 任务条件 | 最小充分结构 | 需要增加的控制 | 增加前应有的证据 |
|---|---|---|---|
| 目标固定、无工具、结果易检查 | 单次调用 | 输入和输出契约 | 任务集显示单次调用不能稳定满足格式或语义要求 |
| 单轮可完成，但材料需要动态选择 | 动态决策视图的单次调用 | 来源、选择、排序、刷新和冲突处理 | 错误可定位到缺失、过期或被淹没的材料 |
| 需要少量有副作用的动作 | 受控环境交互 | 权限、沙箱、预算、日志和确定性反馈 | 仅靠文本约束出现越权、不可见副作用或不可复盘动作 |
| 后续步骤依赖新观察 | 有界反馈推进 | 重试分类、停止、状态提交和任务级验收 | 固定步骤不能覆盖真实分支，且循环收益高于额外失败面 |
| 需要跨会话、分支、恢复或人工接管 | 可恢复的持久执行 | typed state、检查点、显式门和失败去向 | 已出现恢复、审计或依赖关系无法可靠保存在隐式历史中的失败 |
| 长时、高影响、多个执行者和多种恢复路径 | 版本化自适应协作 | 计划版本、责任边界、独立验收和分层恢复 | 受控比较证明新增结构降低错误外溢或恢复成本 |

实施顺序仍然从任务合同开始：

1. **定义决策合同**：目标、受众、完成证据、风险和授权边界；
2. **设计本轮决策视图契约**：每轮需要哪些事实、来源、时态、计划、能力和预算；
3. **确定运行时边界**：哪些规则由代码、权限、沙箱、测试和审批强制；
4. **实现最小跨轮推进**：规定观察、提议、授权、执行、验收、状态提交与停止；
5. **外置高价值控制**：只把反复失败、需要审计或不能交给模型记忆的关系表达为图；
6. **建立人类审查边界**：重要产物应满足[理解、控制与明确决策](./human-review-of-agent-outputs.md)；
7. **用同一任务集做消融**：比较成功率、成本、人工时间、恢复时间、越权、虚假完成和错误外溢。

最佳复杂度随模型能力、任务环境和风险变化。第 5 节收录的厂商工程记录说明，公开的分解和脚手架是针对特定模型、代码任务与已观察失败建立的，同时明确保留跨领域泛化和模型继续演进后的效果问题；它们不能证明模型能力提高后某个组件应自动保留或删除。每个组件都编码了“当前模型、任务与环境做不到什么”的假设；条件变化后，应在相同任务与结果指标上重新消融，以净收益决定保留、增加或删除，而不是按技术年代决定。

## 7. 竞争性解释、边界与反例

- Prompt 改进有时已经足够，额外运行时只会增加延迟和故障面；
- Context 失败可能源于模型能力、检索质量、材料冲突或位置效应，不能统一归因于长度；
- 能力协议可以定义能力协商和可选的传输层授权，但连接权限、安全策略、用户同意和授权决定仍须由宿主或运行环境承担；即使传输授权存在，也不能替代具体业务动作批准、任务调度、完成判定与产物验收；
- Loop 的无限重试可能只需预算和错误分类，不一定需要完整控制图；
- 静态图会固化规划时假设，动态环境可能需要重新规划或允许环的状态机；
- 用于组织推理候选的图与执行控制图处理不同对象，前者的任务收益不能证明后者可靠；
- 多 Agent 或独立评价器可能共享模型、Context 和评价标准，表面分工不会自动产生证据独立性；
- 可视化图容易掩盖节点 Prompt、工具副作用和验收器中的隐含控制；
- 结构化摘要能延长任务，但压缩错误也可能成为下一阶段的“事实”；
- 人类审批按钮无法自动带来有效监督；审查者需要时间、能力、证据和真实拒绝权。

可能显著削弱本文判断的证据包括：在控制模型、任务、预算和工具后，本轮决策视图的选择、模型外运行边界、显式状态与门控没有降低越权、重复失败、虚假完成或复盘成本，并持续损害真实任务成功率。

## 8. 对日常 Agent 使用的意义

以下问题不是要求每个任务生成五份模板，而是用于在关键承诺点暴露控制缺口。低风险任务可以用几句话回答；高影响、长时或多人任务才需要把相关答案保存为可审查制品。

### 指令内容与候选生成

- 目标、受众和成功条件是什么？
- 哪些示例真正改变判断？
- 输出结构怎样被机械检查？

### 本轮决策视图

- 本轮必须看到哪些事实、来源和未决问题？
- 哪些历史只需摘要，哪些原始证据必须保留？
- 哪些信息可能过期、冲突或污染判断？

### 模型外运行责任

- 模型可以提出哪些动作，运行时实际允许哪些动作？
- 工具输入输出是否小而明确，副作用是否可见？
- 状态、制品、日志、权限、预算和密钥保存在哪里？

### 跨轮推进与显式控制关系

- 每轮怎样观察、验收、提交状态和停止？
- 重试、换策略、重规划、回滚和人工接管怎样区分？
- 哪些依赖或门控值得成为显式边，哪些局部探索可以留给模型？

### 人类责任

重要产物需要责任人理解关键内容与逻辑、拥有真实修改或拒绝权，并对限定范围形成明确决定；详细责任条件和边界见[《Agent 产物的人类审查》](./human-review-of-agent-outputs.md)。

无论实现使用什么术语，最低可检查轨迹通常包括：目标与成功证据、当前来源及时态、实际授权与副作用、验收与停止结论。跨轮任务还应留下最后一次已承诺状态和恢复位置。这些是复盘所需的观察证据，不要求创建固定文件、角色或框架。

如果某项约束在模型忘记、误解或反对时仍需成立，应把它移出纯文本指令，由模型外控制执行。如果某项信息不会改变本轮决策，不应仅因“可能有用”就放进本轮决策视图。

## 9. 待区分的问题

只优先研究会改变结构、授权、验收或保留决定的问题。下面不是方案路线图；每项都保留竞争选项，并要求在受控任务中取得能够区分它们的证据。

| 决策对象 | 需要区分的问题 | 足以改变行动的证据 |
|---|---|---|
| 本轮输入与跨轮状态 | 在相同 Token、延迟和维护成本下，原始历史、摘要或类型化状态视图分别何时更少丢失时态、争议与失败证据 | 跨会话任务中的成功率、过期假设传播、恢复时间和可追溯性对照 |
| 模型外控制 | 哪些输入组装、权限、状态、预算和验收责任必须留在模型外；哪些脚手架在模型、指令或任务分解改善后可以删除 | 跨模型与任务的组件消融，测量真实成功、越权、成本和错误外溢 |
| 能力连接与授权 | 连接、发现和传输能力与独立授权策略分离，何时降低越权，何时只增加集成故障和人工负担 | 错误或被拒动作、策略绕过、集成失败和审查时间的对照 |
| 持续执行拓扑 | 在不同依赖密度、环境变化率和恢复需求下，有界循环、状态机、动态有环图或版本化无环图哪一种净收益更高 | 同一任务集上的完成率、重规划损失、恢复时间、审计成本和结构维护成本 |
| 节点与验收契约 | 什么粒度既能独立验收，又不会把开放语义伪装成确定流程；生成的计划、动作 Schema 和验收条件怎样取得独立校验 | 由外部 Oracle 或人工裁决的虚假完成率、接口错误和返工成本 |
| 人类注意力 | 不同影响、可逆性和证据缺口下，哪种审查深度改善最终决定而不是只增加等待时间 | 同等任务与审查者条件下的决策错误、过度依赖、审查时间和认知负担；理解测量由[人类审查分析](./human-review-of-agent-outputs.md)维护 |
| 系统评测 | 哪些轨迹、输入利用、动作、恢复、成本和授权指标比最终答案评分更能预测用户目标是否实现 | 指标与真实任务结果的跨任务关联、失效预警能力和迁移稳定性 |

这些问题的解答可能支持增加结构，也可能支持删除结构。若研究结果不会改变任何选择，只会扩充工具或案例清单，就不属于本文的当前研究任务。
