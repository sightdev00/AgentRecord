# Agent 问题求解的基础控制：问题表征、信念更新、承诺与验收

> 当前判断：Agent 的基础缺陷常发生在问题表征、证据搜索、信念更新、行动承诺和结果验收被压进同一个连续生成过程时。重要产物还需要一项贯穿全程的控制：严密的人类审查。责任人应完全理解关键内容和逻辑结构，能够修改其表达与取舍，并据此作出明确决定。

## 1. 问题是什么

Agent 经常能生成一条局部合理、执行顺畅的路线，却没有证明自己正在解决正确的问题。典型传播过程是：

```text
过窄的问题表征
→ 同源查询
→ 支持性证据占优
→ 暂定假设成为默认事实
→ 围绕该事实规划和执行
→ 用相同前提自我验收
→ 用户接受
→ 错误进入长期记忆
```

“搜索过早收敛”和“过早承诺导致的认知级联风险”可用于概括这条链，但二者目前都不宜冒充边界统一的单一学术术语。前者是多种搜索与判断失效的组合，后者是连接 Agent、人和工程系统的工程化综合概念。

人类位于传播链的关键位置。若审查只剩下浏览最终答案和点击批准，流畅表达会掩盖问题表征、证据和执行中的相关错误。文档、代码和方案即使通过自动测试，也仍可能在意图、逻辑、取舍、风格或决策含义上不受责任人控制。

## 2. 为什么这是 Agent 的基础问题

问题不发生在某个具体模型或工具层，而贯穿认识与行动：

| 控制层 | 核心问题 | 典型失效 |
|---|---|---|
| 问题表征 | 到底在解决什么 | 把症状、用户措辞或初始诊断当成真实边界 |
| 候选空间 | 还有哪些机制和证据方向 | 只做同义查询，只找表面相似案例 |
| 信念更新 | 哪些解释仍然成立 | 锚定、确认偏误、过早闭合 |
| 行动承诺 | 何时允许把判断变成修改 | 证据不足却提前实施 |
| 结果验收 | 什么足以证明完成 | 执行者用相同前提自证成功 |
| 人类审查 | 谁能理解、修改并决定是否接受 | 审查退化为浏览摘要、批准按钮或风格默认 |
| 经验保留 | 什么可以写入长期记忆 | 保存答案，不保存时态、边界和修订原因 |

只提高生成质量无法稳定解决这些问题，因为更强的生成也可能更有说服力地完成一条错误路线。

## 3. 相关概念及边界

### 3.1 任务环境与问题空间

Newell 与 Simon 区分外部世界中的任务环境和求解者构造的问题空间。求解实际发生在问题空间中；表征会决定可见状态、可用操作和停止条件。[Human Problem Solving](https://worrydream.com/refs/Simon_1970_-_Human_Problem_Solving%2C_The_State_of_the_Theory_in_1970.pdf)

面向工程任务，可把问题表征近似写为：

\[
P=\langle G,S,C,M,U,O,R\rangle
\]

- \(G\)：目标与成功标准；
- \(S\)：已观察事实；
- \(C\)：约束和授权边界；
- \(M\)：候选机制；
- \(U\)：未知量与争议；
- \(O\)：可执行的观察、搜索和实验；
- \(R\)：错误行动的成本、可逆性和风险。

用户原始描述是构造 \(P\) 的输入，不是 \(P\) 本身。描述越具体，也可能只是把未经验证的机制隐藏得越深。

### 3.2 查询重构、抽象和类比

查询重构与扩展处理术语不匹配；抽象阶梯和模式抽取把具体问题提升到机制层；类比迁移应对齐因果关系，而非寻找表面相同的故事。结构映射理论强调关系结构及高阶关系的对应。[Structure Mapping in Analogy and Similarity](https://cogsci.ucsd.edu/~coulson/203/gentner-markman-97.pdf)

这些方法不能替代问题表征。若候选机制仍只有一个，增加同义搜索词只会扩大同一条路线的证据量。

#### 动作词不是知识对象

一次实际的仓库结构纠错暴露了另一种表征错误：用户说“调研一个新框架”，Agent 可能把“调研”直接映射为 `research/` 目录，再为它建立专门流程、状态和索引；但被处理的对象仍是视觉模型或框架，它与既有模型、机制和任务的关系并没有因为获取方式是“调研”而改变。

这属于工程观察，目前尚未经过系统实验验证。它与结构映射的要求一致：分类应优先保留对象之间的稳定关系，避免直接复刻句子中的表面词。至少要分开两个问题：

- **对象表征**：这是什么，它在现有体系中与哪些对象同类、依赖或竞争；
- **活动表征**：现在对它做调研、评测、实现、迁移还是复盘。

长期归属主要由对象及其关系决定；活动决定当前采用的证据、流程和输出。只有当活动本身形成了独立、长期、不可被现有对象结构承载的知识对象时，才值得升级为新目录或模块。

#### 权威来源与关系引用

对象与活动分开以后，多个产物仍可能复制同一事实、边界和状态。副本最初一致，不表示以后会同步更新；一旦版本、证据或结论变化，审查者就难以判断哪一处仍然有效。

对准备长期复用的内容，应进一步区分：

- **权威来源**：负责定义事实、版本、证据状态和修订边界；
- **关系引用**：说明该事实怎样被另一个问题、方案或流程使用，不重新维护其定义；
- **案例观察**：保存具体环境中的输入、现象和结果，不能反过来改写通用事实。

“权威”表示维护责任，不表示某个来源垄断真理。相互冲突的主张应保留各自证据和适用范围；关系引用也可以质疑权威条目，但不应悄悄复制并形成第二套事实源。这是近期仓库审校暴露出的工程控制问题，目前尚缺少对不同知识维护结构的系统比较。

### 3.3 CBR、CTA 与 CDM

基于案例的推理以 Retrieve–Reuse–Revise–Retain 为循环，重点是旧经验如何适配、验证和被新案例修订，而非保存“问题—答案”对。[Case-Based Reasoning](https://www.iiia.csic.es/~enric/papers/AICom.pdf)

认知任务分析和关键决策法关注专家在非例行事件中看到的线索、改变判断的时刻、被放弃的选项及反事实条件。它们适合提取教程通常遗漏的判断依据，但回忆材料仍可能有事后合理化偏差，不能直接等同于客观过程证据。[Critical Decision Method](https://go.gale.com/ps/i.do?id=GALE%7CA21159924&issn=00187208&it=r&linkaccess=abs&p=AONE&sid=googleScholar&sw=w&v=2.1)

### 3.4 差异诊断、证伪与信念修订

差异诊断要求同时维护多个原因；证伪要求说明什么观察会削弱当前解释；信念修订研究新信息与旧信念冲突时如何更新知识。[Logic of Belief Revision](https://plato.stanford.edu/entries/logic-belief-revision/)

它们与“列出多个可能原因”不同：真正的要求是让假设产生不同预测，并优先取得能够区分它们的证据。

#### 首个语义分歧边界

复杂链路的最终结果出现差异时，最终症状通常不能直接指出根因。更有区分力的做法是先冻结输入和接口契约，再比较两条路径中语义相同的中间状态，找到第一个显著分歧的边界，然后只在相邻模块内继续下钻。

语义相同比名称或序号相同更重要。不同实现可能融合、拆分或重排步骤；机械对齐“第 N 层”会制造假差异。输入已经不同，就没有依据先归因后续模块；中间状态一致而最终结果不同，则应优先检查下游解释、选择或验收逻辑。

中间输出、数值相似度和可视化只是定位证据，不能代替任务级或系统级 Oracle。若系统不暴露中间状态，应改用能区分候选机制的黑盒输入和输出实验，并保留无法继续定位的不确定性。该方法是对差异诊断的工程化展开，不证明逐层比较在所有系统中成本最优。

### 3.5 人类认知偏差与 Agent 工程失效

Anchoring、confirmation bias、premature closure、automation bias、overreliance 和 cognitive offloading 解释了不同环节的风险。医学诊断文献可提供成熟的结构类比，但这不能证明 LLM 与人脑具有相同内部机制。[Cognitive biases in diagnosis and decision making](https://pmc.ncbi.nlm.nih.gov/articles/PMC8520040/)

因此，本文使用这些概念描述可观察行为和系统结构，不对模型内部心理机制做未经证实的拟人化判断。

### 3.6 人类审查：理解、控制与决策

Human-in-the-loop 在许多 Agent 工具中主要表现为敏感工具调用前的批准或拒绝。例如 [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/human_in_the_loop/) 可以在工具执行前中断、序列化状态，并由人决定批准或拒绝。这是重要的行动门控，但还不能覆盖文档、代码和方案的完整审查。

任何准备交付、合并、发布或作为决策依据的文档、代码和方案，都应经过能够承担责任的人类审查。本文把严密审查定义为三个同时成立的完成条件。

#### 完全理解关键内容和逻辑

责任人应能脱离 Agent 的结论摘要，准确说明：

- 产物解决什么问题，成功标准和适用边界是什么；
- 核心结构、关键推理链或主要状态转移怎样组成；
- 哪些结论由直接证据支持，哪些属于推断、选择或暂定假设；
- 主要风险、竞争解释、失败条件和剩余未知量是什么；
- 对代码，重要数据流、权限、副作用、测试和回滚点在哪里；
- 对方案，关键取舍会让谁承担什么成本，并影响哪些后续决定。

“完全理解”针对重要内容与逻辑结构，不要求逐字背诵或人工重做每个机械步骤。若责任人无法用自己的语言重建主要判断，就没有条件为产物负责。

#### 控制内容、结构与叙述风格

责任人需要真实的编辑权和否决权：

- 可以修改目标、结构、术语、证据权重和方案取舍；
- 可以要求重写不符合团队或个人风格的表达；
- 可以删除机械对称、空泛总结、虚假完整感和过度使用的对照句式；
- 可以拒绝“像 AI 写的”但逻辑、语气或审美不合格的文本；
- 可以要求代码按人类可维护的边界重构，即使现有测试已经通过；
- 可以查看原始材料、diff、测试和运行结果，而非只看 Agent 的自我解释。

叙述风格属于产物质量的一部分。诸如“是……而不是……”的密集对照、统一节奏的段落、无实际内容的标题和模板化收束都可以成为审查信号。它们不是一律禁止的语法；责任人应判断表达是否服务于真实区别，并拥有最终选择权。

[Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf) 经多轮评估提出了支持纠正、说明系统行为原因、接受细粒度反馈和提供全局控制等原则。这些研究支持“人必须能理解和改变系统行为”的方向，但没有直接验证本文针对 Agent 产物提出的三项审查合同。

#### 基于内容作出清晰决策

审查需要落到可执行结论：

```text
Accept    接受，并明确适用范围和责任人
Revise    退回修改，并指出证据、逻辑、风格或实现缺口
Reject    拒绝当前方向，保留理由和替代路径
Escalate  信息、权限或专业能力不足，交给合适的人继续判断
```

“已阅读”“看起来可以”“测试通过”没有说明接受了什么风险，也没有给出后续行动。有效决定至少记录决定内容、依据、剩余风险、责任人和下一步。

决定还必须限定维度和范围。接受目录或接口结构，不等于接受其中的技术事实；接受技术解释，不等于接受工程结果或发布风险。一个产物可以同时处于“结构已接受、事实待核、结果未验证”的状态。用一个全局“已审查”标记覆盖这些差异，会让局部决定越权传播为整体认可。

[Appropriate reliance](https://arxiv.org/abs/2204.06916) 研究把适当依赖描述为分辨 AI 建议质量并据此行动的能力；仅提高对 AI 的信任或提供解释都不能稳定保证决策质量。人类审查的目标因此应放在判断与行动质量上，而非批准率。

可以把审查合同写成：

\[
R_h=\langle U,C,D,E\rangle
\]

- \(U\)：理解证据，证明责任人掌握关键内容与逻辑；
- \(C\)：控制能力，能够编辑、拒绝、回退和改变风格；
- \(D\)：明确决定，包含范围、责任和后续动作；
- \(E\)：审查所依据的原始证据、diff、测试、日志和来源。

当 \(U\)、\(C\)、\(D\) 任一缺失时，Human-in-the-loop 只表示流程中出现过一个人。

#### 理解确认门

关键决策可以增加一道理解确认门。Agent 先提交决策包，再要求责任人用自己的语言说明理解，最后才开放批准、修改、拒绝或升级。

决策包至少包含：

- 当前需要决定什么，为什么必须现在决定；
- 可选方案、Agent 建议及主要取舍；
- 关键事实、假设、证据和未决问题；
- 主要风险、不可逆后果和影响对象；
- 哪些新证据会改变当前建议；
- 批准后系统将执行的具体动作。

确认问题应检查理解，避免只问“你理解了吗”。例如：

1. 请用自己的话说明当前决策及其目的；
2. 这个方案最重要的风险和不可逆后果是什么；
3. 还有哪些可选方案，当前方案为什么获得推荐；
4. 哪项事实仍是关键假设；
5. 出现什么新证据时应暂停或改变决定。

Agent 在提出问题前，应根据决策合同记录理解标准。标准列出必须覆盖的概念、关键误解和允许的语义等价表达。责任人的回答缺少关键内容时，状态进入 `NEEDS_CLARIFICATION`；Agent 指出具体缺口、提供原始证据并再次确认。只有达到标准后，状态才能进入 `COMPREHENSION_CONFIRMED`。

```text
PENDING_COMPREHENSION
→ NEEDS_CLARIFICATION
→ COMPREHENSION_CONFIRMED
→ DECISION_PENDING
→ ACCEPT / REVISE / REJECT / ESCALATE
```

理解与同意必须分开。责任人反对 Agent 建议、使用不同术语或提出新的合理取舍，都不能被判定为“不理解”。“输入合理”表示回答覆盖了关键事实、逻辑、风险和后果，并与可核查证据相容；它不要求人类接受 Agent 的偏好。

Agent 同时担任提案者、解释者和唯一考官时，会形成相关失败：错误决策可能生成一套维护自身错误前提的问题与评分标准。高影响场景应让理解标准引用独立规则和原始证据，并增加领域专家、第二位审查者或确定性检查。Agent 可以检查回答是否完整，不能垄断“什么意见才合理”的定义。

## 4. 已有证据

目前的证据强度并不均匀：

- 问题表征限制搜索空间，具有经典问题求解理论基础；
- 锚定、过早闭合等概念在人类判断研究中证据较成熟，但映射到 Agent 主要是结构类比；
- Agent 记忆研究开始区分材料召回与状态承诺，支持“检索不等于事实写入”的工程方向。[AI Agents Need Memory Control Over More Context](https://arxiv.org/html/2601.11653v1)
- 认知 Agent 架构研究表明 reasoning、planning、memory 和 action 的抽象仍不统一，这支持建立更清楚的状态边界，但不直接证明某一控制结构最优。[Cognitive Architectures for Language Agents](https://arxiv.org/html/2309.02427v3)
- “同一 Agent 的反思不足以独立验收”主要来自共享上下文、证据和目标所导致的结构性相关；现有证据不支持“反思永远无效”这一更强结论；
- Human-AI interaction 研究支持可理解、可纠正、可反馈和可全局控制的交互原则；appropriate reliance 研究强调人需要分辨建议质量并据此行动；
- [NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/) 要求明确人机配置中的角色与监督责任，并指出文档可以改善人类审查与问责。这是治理框架证据，不是“所有产物采用同一审查流程”的实验结论；
- “理解—控制—决策”三项审查合同是本文基于上述研究与 Agent 工作流提出的工程判断，尚缺少针对生成式文档、代码和方案的统一实证。
- “知识整合与任务激活分离”“权威来源与关系引用”“首个语义分歧边界”和“限定审查维度”来自近期仓库治理与工程诊断观察。它们与状态分离、差异诊断和可纠正的人类审查方向一致，但尚未经过跨任务、对照化的统一实验。

现有材料足以支持风险模型和设计原则，还不足以证明一套通用流程能在所有 Agent 任务中提高成功率。

## 5. 竞争性解释

至少需要保留以下解释，避免把所有失败都归因于过早收敛：

1. **能力不足**：模型没有理解关键机制，即使给出正确表征也无法求解；
2. **证据不可得**：正确区分需要的日志、权限或实验条件不存在；
3. **目标不清**：用户和 Agent 对成功标准本就不一致；
4. **成本约束**：系统有意在有限时间和 Token 下使用满意化停止规则；
5. **执行错误**：问题和假设正确，但代码、工具调用或环境操作失败；
6. **验收器错误**：Oracle 自身不可靠或覆盖不足；
7. **记忆污染**：过期状态或用户假设被当成当前事实；
8. **激励错配**：系统更奖励快速给出完整答案，而非保留不确定性；
9. **审查条件不足**：审查者缺少时间、领域能力、原始证据、真实修改权或拒绝权；
10. **审查相关失败**：人和 Agent 共享同一错误表征，人工参与没有带来新的证据或视角。
11. **控制形式化过载**：状态、模板、重复权威声明和审查门本身占用了理解与维护能力，反而掩盖真正需要决定的内容。

这意味着不能把“多搜索”“列更多假设”或“加一个人工批准点”当成统一修复；控制强度必须随歧义、后果、不可逆性和证据缺口变化。

## 6. 当前判断

可靠 Agent 至少需要显式区分四类状态：

1. **Problem state**：目标、事实、约束、未知量和替代表征；
2. **Belief state**：竞争假设、支持与反对证据、未验证假设；
3. **Commitment state**：哪些只是候选，哪些已获准进入行动，以及撤销条件；
4. **Verification state**：什么新鲜、独立的证据足以接受、拒绝或回滚。

知识整合、技术验证和任务激活属于不同承诺。信息基线经过审查，表示其结构和证据边界可以在限定范围内使用；它不会自动授权实验、实现、部署或发布，也不表示技术内容已经验证。行动应由真实需求、授权、待区分问题和验收条件触发，不能由文档的完整感触发。

人类审查贯穿四类状态，并在重要承诺与产物发布前形成独立的 Review contract。审查者要看到与当前决定相关的状态、原始证据和实际制品，完成理解、控制和决策三项工作。系统可以记录审查，不能替审查者承担决定。

检索到的信息只能成为候选证据，不能自动变成当前事实；能够执行某个动作，也不等于已经获得该动作的授权；执行者生成的解释，也不等于独立验收；人类点击批准，也不证明其理解了产物。

在选择目录、工具、Agent 角色或工作流之前，还应先做一次“对象—活动”分离：目录回答内容长期属于什么，流程回答当前怎样处理它。不能仅凭用户使用了“调研”“评测”“部署”“复盘”等词，就创建同名知识域。判断新结构是否必要，至少要检查：去掉动作词后对象是否仍无法归入现有体系；新结构是否表达了新的稳定关系；它是否会与现有索引、状态或证据规则重复。

下一步实验应优先按区分能力、成本、风险和可逆性排序：

\[
a^*=\arg\max_a
\frac{\mathbb{E}[\Delta I(H;E\mid a)]}
{Cost(a)+Risk(a)}
\]

工程中不必伪造精确概率。只需明确每项测试能排除哪些假设、不同假设预期看到什么、失败结果是否仍提供信息。

对于文档、代码和方案，可在发布或交付前增加以下审查门：

```text
关键内容与逻辑能否由责任人独立复述？
→ 不能：补证据、重构或解释
→ 能：责任人能否直接修改内容、结构与风格？
    → 不能：恢复编辑权与原始材料访问
    → 能：是否形成 Accept / Revise / Reject / Escalate 决定？
        → 否：审查未完成
        → 是：记录依据、范围、风险、责任人和下一步
```

## 7. 适用边界与反例

- 目标清楚、改动可逆且已有确定性测试的简单任务，不需要完整假设账本；显式状态、模板和审查门本身也有理解与维护成本，应只保留能够改变行动或验收的最小充分控制；
- 探索性写作和创意生成不总有唯一 Oracle，验收应转向约束满足、风格控制和人工选择；
- 独立 Agent 不天然等于独立证据；若共享表征、材料和评判标准，多 Agent 仍可能相关失败；
- 保留过多假设会产生分析瘫痪，候选集合应由可观察预测和风险约束；
- 外部 Oracle 也可能错，因此高风险任务需要验证 Oracle 本身；
- “搜索过早收敛”只解释一部分失败，不能替代能力、数据、执行、权限和目标诊断；
- 人工审查会受自动化偏见、疲劳、时间压力和领域盲区影响，增加人并不自动提高质量；
- 完全理解的深度应随影响和复杂度调整。机械生成的低风险中间文件可以抽样或用确定性检查；最终文档、核心代码和决策方案需要责任人理解其中的重要内容与逻辑；
- 解释可能降低核查成本，也可能用流畅叙述提高错误建议的可信度；审查应保留原始证据和独立检查路径；
- 风格审查不能代替事实、逻辑和安全审查，事实正确也不能剥夺责任人对表达与取舍的控制。

可能推翻或显著削弱本文判断的证据包括：在控制任务难度和成本后，显式分离这些状态以及加入具备理解、控制和决策条件的人类审查，没有降低错误承诺或虚假完成，反而稳定降低真实任务成功率。

## 8. 对日常 Agent 使用的意义

日常使用不需要先建设复杂平台，可以先改变关键承诺点：

1. 在解决前区分目标、观察事实和用户当前诊断；
2. 在选目录、工具或流程前区分“对象是什么”和“现在对它做什么”，并明确谁负责维护事实、谁只表达引用关系；
3. 对高歧义问题保留至少一个机制不同的替代解释；
4. 搜索时覆盖机制、上下游、原始来源和反证，而非只改写原句；
5. 把知识整合、技术验证和任务激活当作不同承诺；修改前说明该动作能区分什么、不能区分什么；
6. 高影响动作必须给出授权边界、剩余不确定性和回滚条件；
7. 复杂链路先锁定输入和接口，定位首个语义分歧边界；再用新鲜输出、测试、日志和实际制品验收，不以 Agent 自述或单一相似度为证；
8. 在关键决策前提交决策包，并用预先记录的理解标准检查责任人能否复述目标、逻辑、证据、风险、替代方案和后果；
9. 理解不足时指出具体缺口并继续澄清，不接受简单的“我已理解”；
10. 给责任人完整的 diff、来源、测试和编辑权，使其能够调整内容、结构、代码和叙述风格；
11. 把理解与同意分开，允许责任人在充分理解后反对 Agent 建议；
12. 审查结束时记录 Accept、Revise、Reject 或 Escalate，以及依据、范围、责任人和下一步；
13. 写入长期记忆时区分偏好、假设、事实、决策、历史状态和争议。

这些是控制原则，不是必须固化为若干 Skill 或若干角色。只有当重复失败证明某一步需要机器检查时，才值得产品化。人类责任也不能通过增加一个名为 Reviewer 的 Agent 来替代。

## 9. 未解决问题

- 如何测量“问题表征正确性”，而不依赖另一个同样可能偏置的模型？
- 怎样设定停止规则，兼顾反证覆盖与时间、Token 成本？
- 何种独立性足以让验收器真正降低相关失败？
- 如何让记忆保留时态和争议，又不产生维护负担？
- 哪些任务适合显式信念状态，哪些任务只需轻量检查？
- 用户看到多少不确定性最有助于校准，而不会造成认知过载？
- 怎样证明审查者理解了关键逻辑，同时避免把审查变成背诵、考试或形式化打勾？
- 哪些界面能让人控制叙述风格和结构，又不会把编辑负担全部转嫁给人？
- 如何测量审查是否改善了最终决策，而非只增加等待时间或降低自动化率？
- 当责任人、领域专家和受影响者不是同一个人时，决定权与审查职责怎样分配？
