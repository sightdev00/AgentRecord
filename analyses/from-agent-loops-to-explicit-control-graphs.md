# 从 Agent Loop 到显式控制图：执行结构何时值得被外置

> 当前判断：从 Agent Loop 转向显式图的核心，不是把一个 Agent 拆成更多节点，而是把部分调度权从模型的即时生成中移出，变成可检查的依赖、门控、预算、恢复和验收约束。图能提高可控性，但不会自动提高推理正确性；简单、低风险、强可逆的任务仍可能更适合 Loop。

## 1. 问题是什么

典型 Agent Loop 可以压缩成：

```text
读取目标与历史
→ 模型决定下一步
→ 调用工具或生成答案
→ 把结果追加到上下文
→ 模型判断继续、重试、改道或结束
```

它的优点是开放和灵活：模型可以根据新观察临时改变路线，不必预先枚举所有分支。问题也来自同一处——“下一步是什么”“失败后怎么办”“什么算完成”可能都由同一次生成决定，并隐藏在不断增长的自然语言上下文里。

因此，真正的问题不是 Loop 能否循环，而是：

1. 哪些决策可以继续交给模型的任务内策略；
2. 哪些约束必须独立于模型，成为系统可检查的控制状态；
3. 当计划需要改变时，怎样保留旧计划、执行事实和修订原因，而不是改写一段看似连贯的历史。

显式控制图是这一问题的一种答案，但不是唯一答案，也不是所有任务的默认答案。

## 2. 为什么这是 Agent 的基础问题

语言模型擅长在开放空间中生成候选动作，却不天然提供持久、可验证的执行语义。Agent 系统至少同时处理三类不同对象：

| 对象 | 回答的问题 | 典型载体 |
|---|---|---|
| 决策策略 | 根据当前信息，下一步可能做什么 | 模型推理、规则或规划器 |
| 控制规范 | 哪些动作现在被允许，依赖、预算和门控是什么 | 图、状态机、工作流或代码 |
| 执行事实 | 实际发生了什么，产生了什么输出和错误 | 事件日志、制品和验收记录 |

纯 Loop 容易把三者都折叠进对话历史：模型既提出路线，又解释路线是否合法，还根据自己生成的摘要判断路线是否成功。显式图的基础价值是把其中一部分关系外置，使调度器、人和验收器不必重新解释整段自然语言才能知道“现在允许发生什么”。

这与上一篇分析中的问题表征、信念、承诺和验收控制相连，但焦点不同：那里讨论认识状态怎样约束行动；本文讨论已经进入执行后，控制拓扑和运行历史怎样被表达。

## 3. 相关概念及边界

### 3.1 Loop、控制图和执行轨迹不是同一个对象

- **Loop** 是运行时的重复结构。图执行器本身也可以由一个事件循环驱动，因此“Loop”与“图”并非实现层面的对立物。
- **控制图** 描述允许或计划中的执行关系。节点可以是动作、检查点或子流程；边可以表达依赖、条件、失败转移或授权门。
- **执行轨迹** 是一次运行实际经过的节点、输入、输出、错误和决策。它通常只是控制图中的一条展开路径，并可能包含重试和重规划事件。
- **思维图或知识图** 表达信息单元之间的推理、组合或语义关系，不必规定工具调用的授权与调度。

[Graph of Thoughts](https://arxiv.org/abs/2308.09687) 把 LLM 产生的信息单元作为顶点、依赖作为边，并在特定任务上报告了收益。这是“推理对象图”的直接证据，不是“执行控制图优于 Loop”的直接证据。名称里都有 graph，不能据此合并两类主张。

### 3.2 调度器视角

[From Agent Loops to Structured Graphs](https://arxiv.org/abs/2604.11378) 把 Agent Loop 解释为一种 ready set 大小至多为一、且选择策略主要隐藏在模型推断中的调度器；它提出 Structured Graph Harness，以静态 DAG、版本化计划、上下文分离和分层恢复换取可控性。

这个视角有用，因为它把争论从“哪种 Agent 框架更先进”改写为：

```text
系统状态 s
→ 可执行集合 U(s)
→ 选择策略 P
→ 观察与状态转移
```

Loop 与图都可以放进这个统一描述。差别不在是否存在调度，而在可执行集合、选择策略和转移条件有多少被写成模型外部可检查的对象。

但该论文明确把自己定位为立场论文和设计提案：它给出形式化规格和未来实验方案，没有生产实现或经验结果。因此，论文足以支持一种清晰的问题重构，不能单独证明静态图在真实 Agent 任务上更可靠。

### 3.3 “显式”至少需要什么

一张可视化连线图不一定具有明确控制语义。最低限度上，显式控制节点应能回答：

- 输入来自哪里，哪些前置条件必须成立；
- 允许产生什么输出，输出由什么检查；
- 成功、失败、跳过和取消分别是什么终态；
- 谁可以触发执行、重试、升级、回滚或重规划；
- 重试次数、时间、Token、费用和风险预算是多少；
- 哪些事件属于不可改写的执行事实。

边也不只是“接下来可能到这里”的箭头。依赖边、条件边、数据边、失败边和授权边若语义不同，就应在规格或运行时中可区分。否则，图只是把隐含 Loop 换成了隐含连线。

### 3.4 静态图不等于永不变化

“执行中的计划版本不可变”与“系统不能重规划”可以同时成立。更准确的做法是：

```text
计划 v1 --执行到节点 n、发现新事实--> 提出计划 v2
计划 v1 --保留已发生事件与停止原因--> superseded
计划 v2 --通过新的门控后--> 继续执行
```

不可变的是已经承诺的计划版本和已发生的执行事实，不是 Agent 对世界的永久判断。若系统直接在原图上悄悄改边，复盘时就无法分清原计划、运行时偏离和事后解释。

## 4. 已有证据

目前证据支持“控制关系值得外置”，但尚不足以支持“静态 DAG 普遍优于 Agent Loop”。

### 4.1 对 Loop 能力与局限的直接证据

[ReAct](https://arxiv.org/abs/2210.03629) 通过交错生成 reasoning、action 和 observation，在问答、事实核验及交互环境上展示了 Loop 式决策的有效性。它说明模型根据新观察动态调整计划不是缺陷，而是 Agent 适应性的来源。

同一论文也记录了轨迹上下文带来的失败：模型可能无法正确理解前序观察，继续生成幻觉动作。这个结果支持“仅把历史继续塞回模型并不保证正确状态跟踪”，但不能区分错误来自上下文表示、模型能力、提示设计还是 Loop 控制结构。

[Cognitive Architectures for Language Agents](https://arxiv.org/abs/2309.02427) 把语言 Agent 描述为在环境中重复决策的循环，同时区分工作记忆、长期记忆、内部动作、外部动作和决策过程。这说明 Loop 可以是更大架构的外层时序，而不是必须被图消灭的简陋方案。

### 4.2 来自控制系统研究的结构类比

[Statecharts](https://doi.org/10.1016/0167-6423(87)90035-9) 用层级、并发和通信扩展传统状态图，以表达复杂离散事件系统。[Workflow Patterns](https://www.workflowpatterns.com/patterns/control/) 则系统化了顺序、选择、并发、同步、多实例和取消等反复出现的控制流需求。

这些工作直接证明了显式控制形式在传统反应式系统和工作流中的表达价值。映射到 LLM Agent 仍属于结构类比：LLM 节点的输出是概率性的、语义开放的，节点是否“成功”往往也需要不完美的验收器，不能直接套用确定性工作流的保证。

### 4.3 对结构图方案的直接但未完成证据

Structured Graph Harness 论文调查了 70 个系统，并给出节点状态机、恢复协议、终止和健全性主张以及七组实验设计。它最有价值的贡献是把计划承诺、执行上下文和诊断上下文分开，并明确承认可控性、表达力与实现难度之间的交换。

但“调查到某种失败常见”仍主要是定性观察；形式保证也只在规格假设成立时有效。没有完成对照实验之前，真实成功率、恢复成本、计划过时率和人工负担仍是未知量。

## 5. 竞争性解释

观察到 Agent 重复、偏航、难以调试时，至少还应考虑：

1. **可观测性不足**：Loop 本身可行，只是没有结构化事件日志和稳定的运行 ID；
2. **预算缺失**：无限重试来自没有次数、费用或时间上限，不一定需要完整图；
3. **状态提取错误**：模型没有从观察中提取正确事实，换成图仍会把错误状态传下去；
4. **验收器错误**：节点满足了形式化输出 Schema，但语义结果仍然错误；
5. **计划过早固化**：环境变化频繁，静态图使旧假设获得了不应有的权威；
6. **图生成错误**：由同一个模型生成节点、依赖和验收条件，只是把错误从运行时提前到了规划时；
7. **编排复杂度**：节点切分、状态持久化和恢复逻辑增加了新的实现及运维故障面；
8. **任务本来简单**：单路径、低风险任务的主要成本来自模型调用，图不会提供有意义的控制收益。

因此，Loop 的失败不能自动成为图的成功证据。需要比较的是同一任务、同一模型和相近预算下，不同控制外置程度带来的净变化。

## 6. 当前判断

更准确的方向不是“用图替代 Loop”，而是建立**可变的策略内核与不可绕过的控制外壳**：

```text
模型或规划器：提出候选动作、局部顺序和重规划
                    ↓
控制外壳：检查依赖、权限、预算、风险、版本和门控
                    ↓
执行器：产生新鲜输出与不可改写事件
                    ↓
验收器：依据节点契约接受、拒绝、重试、升级或回滚
```

以下情形越多，越值得把控制关系显式化：

- 存在三个以上非线性依赖、并发或汇合关系；
- 动作昂贵、不可逆、面向外部人员或涉及高权限；
- 失败后需要区分重试、换策略、重规划、人工接管和回滚；
- 任务需要暂停、恢复、重放、审计或跨进程运行；
- 完成必须由与执行不同的证据或角色验收；
- 多个 Agent 或工具共享同一批状态和制品；
- 必须证明某些路径不可能发生，或某些门控无法绕过。

以下决策通常可以保留在 Loop 内：

- 低风险、可逆的局部探索；
- 搜索词、阅读顺序和临时草稿等微观策略；
- 尚未稳定到足以预先枚举的开放问题；
- 失败可由确定性测试快速暴露的短任务。

图的最小单位不应是“调用一次模型”，而应是一个有控制意义的承诺：明确输入、输出契约、权限、预算、终态和失败去向。切得过细会把自然语言推理伪装成精确流程；切得过粗则继续隐藏关键转移。

## 7. 适用边界与反例

- DAG 适合有界、可版本化的执行计划，不适合直接表达永久运行的反应式循环；后者可能需要状态机、事件系统或允许环的过程模型；
- 可视化不是必要条件。机器可检查的代码、状态表或事件规则也可以是显式控制；
- 显式图保证的是转移结构，不保证问题表征、节点语义、工具输出或验收 Oracle 正确；
- 动态环境中，频繁重规划可能使图版本管理成本高于收益；
- 多 Agent 图不会自动产生证据独立性，共享模型、上下文和评分器仍会相关失败；
- 简单任务中，固定工作流可能降低适应性，并增加延迟与维护成本；
- 形式上的 termination 只能证明调度过程在给定假设下停止，不能证明停止时用户目标已经真实满足。

可能推翻或显著削弱本文判断的证据包括：在高影响、长时、可恢复任务的受控比较中，外置依赖、预算、恢复和验收关系没有降低越权、无限重试、虚假完成或复盘时间，反而在相近成本下持续降低真实任务成功率。

## 8. 对日常 Agent 使用的意义

不需要先引入图框架，也可以把关键控制从 Loop 中移出来：

1. 把“下一步建议”与“下一步已获准执行”分开；
2. 在高影响动作前写清依赖、授权、预算和回滚条件；
3. 为重试设置上限，并区分原样重试、换策略和重新规划；
4. 让节点输出指向实际制品、日志或测试，不只保存模型摘要；
5. 把验收条件写在执行前，并尽量使用新鲜、独立的证据；
6. 重规划时创建新版本，保留旧计划停止位置和触发原因；
7. 先从反复出现的失败边界外置控制，不为所有任务预建完整图；
8. 评估系统时同时记录成功率、成本、人工介入、恢复时间和错误外溢，而非只看最终答案。

日常实践中的判断标准可以压缩为一句话：如果某个约束在模型忘记、误解或反对时仍必须成立，它就不应只存在于 Prompt 或对话历史中。

## 9. 未解决问题

- 怎样测量“可控性”的收益，而不把流程更长误当成更可靠？
- 节点应按工具调用、语义子目标、风险承诺还是验收单位切分？
- 哪些任务适合静态 DAG，哪些需要状态机、动态有环图或纯 Loop？
- 由模型生成的图应经过哪些结构和语义检查，才能进入执行承诺？
- 计划版本、执行事件和诊断上下文应如何分离，又不造成信息丢失？
- 怎样验证恢复策略不会把暂时故障升级为重复副作用？
- 图外置了哪些控制，又有哪些关键决策仍然隐藏在节点 Prompt 和验收器里？
