# Repository instructions for agents

AgentRecord is a narrow, personal repository for durable analysis of agents themselves.

When adding or revising content:

1. Put new substantive writing in `analyses/`.
2. Do not create new top-level directories or new asset types without first presenting an exact change list to the user.
3. Before writing from a conversation or task, inspect the ownership map in `README.md`, `_meta/writing-guide.md`, and the existing analyses. A valid review outcome may be no repository change.
4. Apply this admission order: without stable evidence or a traceable artifact, do not record it; for the same core question, revise its owning analysis; create a new analysis only for an independent question with its own evidence, competing explanation, and validity boundary.
5. Keep one authoritative analysis for each core question. Other analyses should link to it and state their interface, not duplicate its argument or evidence map.
6. Organize analyses around stable agent problems and mechanisms. Named tools, frameworks, models, and workflows may be evidence or examples, but not long-term classification axes.
7. Do not add domain engineering implementations, project logs, tool tutorials, news summaries, prompt collections, or skill collections.
8. An external case may be cited as evidence, but its background, commands, experiment output, and solution stay in its domain repository.
9. A new article must form an independent judgment; a source roundup or chat summary is not enough.
10. Separate verified facts, structural analogies, inferences, hypotheses, and conclusions.
11. Prefer primary sources, search for counterevidence, and state uncertainty, validity boundaries, and shared dependencies among supporting sources.
12. Choose proactive research by its ability to distinguish a current unresolved question and change a judgment or action; novelty and popularity are not priorities.
13. Do not treat user beliefs, case descriptions without traceable artifacts, retrieved memories, popularity, or model self-review as factual evidence. Use them to locate questions and evidence, not to establish general mechanisms.
14. Revise an existing article when new evidence changes the same question; do not create parallel documents merely to preserve old wording.
15. When touching an analysis or changing the ownership map, recheck that it still owns an independent stable question and still has evidence for its current judgment. If not, prepare an exact consolidation and removal list; after any required structural confirmation, merge surviving content into the proper owner, repair links and the index, and remove the obsolete article. Git history preserves superseded text, so do not keep duplicate authorities merely as archives.
16. Prefer one clear thematic commit over file-by-file commits.

Before changing repository structure, list the proposed changes and wait for user confirmation.
